# UI Canvas 上手指南：從安裝到完成第一輪畫面討論

## 這是什麼

你手上有 PRD 或需求，但還沒有設計稿。`ui-canvas` 讓 AI 用專案裡現成的元件，把這個功能的每個畫面和狀態做成可以實際操作的預覽，像 Figma 一樣把好幾張畫面攤在同一個可以拖動、放大縮小的畫布上。你在瀏覽器上點某個區域留言；AI 在你原本的 CLI 裡處理，改完回覆在同一則留言下。討論收斂後，AI 產出 UI spec 和交接文件，給後續實作參考。

幾件先講清楚的事：

- **Codex CLI 和 Claude Code 用法完全一樣。** 同一個 skill、同一套流程，只差觸發字：Codex 打 `$ui-canvas`，Claude Code 打 `/ui-canvas`。不需要開 ChatGPT App 或任何第二個 AI。
- **審閱畫面是 local review 的本地網址，不是檔案。** AI 會給你類似 `http://127.0.0.1:4318` 的網址（4318 是預設 port，被佔用時會換），用一般瀏覽器打開就好。下文都叫它「審閱網址」。
- **瀏覽器不會自動叫 AI。** 你留完幾則留言後，回原本的 CLI 說一句「已留言」，AI 一次處理一批。
- **不限專案。** 任何能在本機跑起來的 Web 專案都可以，接入是 AI 的工作。目前實際驗證過的是 React + Storybook 的專案；其他框架第一次用會多一些探索時間。

## 1. 安裝

一行指令，Claude Code 和 Codex 一起裝：

```sh
npx skills add amyyi/agent-sdlc --skill ui-canvas -g -a claude-code -a codex -y
```

只用其中一個的話，把不需要的 `-a …` 拿掉。這個指令抓的是 GitHub 上已發布的版本；如果它說找不到 `ui-canvas`，代表這版還沒發布，改用下面的方式。

如果分享者給你的是 repo 的某個 commit 或 tag，就自己複製一份：

```sh
git clone https://github.com/amyyi/agent-sdlc.git
cd agent-sdlc
git checkout <分享者給的 tag 或 commit>

mkdir -p "$HOME/.claude/skills/ui-canvas" "$HOME/.agents/skills/ui-canvas"
cp -R skills/ui-canvas/. "$HOME/.claude/skills/ui-canvas/"   # Claude Code
cp -R skills/ui-canvas/. "$HOME/.agents/skills/ui-canvas/"   # Codex
```

**怎麼確認裝好了：**安裝目錄下直接有 `SKILL.md`（不是多包一層 `ui-canvas/ui-canvas/`）。然後**開一個新的 CLI session**，打 `/ui-canvas` 或 `$ui-canvas`，AI 應該會回應要開始 UI 討論、問你 PRD 在哪。舊 session 不會讀到新裝或更新的 skill，每次更新後都要開新的。

## 2. 開始前你要準備的

- Node.js 20 或以上。終端機打 `node --version` 看一下。審閱工具只用 Node 內建功能，不用 `npm install`，也不需要模型 API key。
- PRD 檔案路徑，或直接貼需求文字。
- 前端 repo 在你電腦上的位置。這是選填：AI 會自己從路由和 import 找出這個功能屬於哪個 repo；你在前端 repo 裡開 CLI，或路徑放在它讀得到的地方，通常不用給。給了可以省掉它找的時間，電腦上有好幾個相似 app 時尤其有用。後端 repo 同理。
- 專案要能在你的電腦上跑起來。私有套件、環境變數、登入權限這些要你先弄好，AI 幫不了。

你不需要先知道專案用了哪些元件、什麼 CSS。那是 AI 要去探索的。

## 3. 一輪怎麼跑

### 3.1 在 CLI 貼需求

在前端 repo 開一個新的 CLI session，貼上這段（先換掉 `<…>`）：

```text
/ui-canvas

我要討論 UI，產出可供後續實作的 UI spec 與可操作 layout。
PRD：<PRD 檔案路徑；沒有檔案就直接貼需求>
FE repo：<本機路徑；讓 AI 自己找的話這行可以刪>
BE repo：<本機路徑；沒有或讓 AI 自己找就刪掉這行>
本次輸出目錄：.ui-canvas/<功能名稱>/

請先探索實際框架、共用元件與相似畫面，再提出可由既有元件組成的方案。
使用 bundled local review，把這個功能的各個畫面／狀態排在同一個畫布上，讓我在一般瀏覽器操作預覽並留言，留在目前 CLI 處理。
預覽啟動、可留言區域設定、review-manifest.json 都由你負責；不要只給我 Storybook 網址。
不明確的業務規則列出選項、影響與決策人，不擅自決定。
這輪只做 UI 設計預覽與 spec，不實作正式產品功能，不 commit 或 push。
```

Codex 把第一行換成 `$ui-canvas`，其他不用改。這整段是給 AI 的指示，不是 shell 指令。

**你會看到：**AI 先說明會沿用哪些現成元件、有哪些取捨，然後把專案預覽和審閱服務跑起來，最後給你一個 **審閱網址**（local review 的本地網址）。如果缺私有套件或環境，它應該具體說缺什麼，而不是拿截圖充當預覽。

### 3.2 打開審閱網址，看整個流程

用瀏覽器開 AI 給的審閱網址。畫面分三塊：

- **上方一排「流程」按鈕**：每個畫面或狀態一顆，有編號。點一下會移到那張畫面。
- **中間畫布**：所有畫面攤開排在一起，一開始都是縮圖（或灰色佔位卡）。滾輪平移，⌘（或 Ctrl）+ 滾輪縮放，按「全部顯示」一次看全部。
- **右側面板**：留言框和討論紀錄。

縮圖只能看，不能點裡面的東西。要操作某張畫面，**點一下縮圖**（或按標題列的「開啟即時畫面」），它會變成真正跑起來的元件，可以打字、開關對話框、按按鈕。

畫布上同時最多 3 張畫面是「活的」（可以實際操作的）。開第 4 張時，最早打開的那張會變回縮圖。這只影響能不能操作那張畫面，不影響留言：留言想留幾則、留在幾張畫面都可以，被收回的畫面點一下就再打開，上面的留言和釘子都還在。

開好後看工具列，應該顯示「**已連接 · N 個可留言區域**」，N 大於 0。這才代表那張畫面可以留言。頁首下方那行「已連線」只是說留言服務通了，不是同一件事。

AI 想問你的事會出現在畫布上（問號釘子）和右側「待你決定」；點候選答案或自己打字，儲存後回 CLI 說「已留言」。

### 3.3 留言

1. 用上方流程按鈕切到你要講的畫面。
2. 按工具列的「**選取區域留言**」。如果那張畫面還是縮圖，它會自動先開起來（按鈕會短暫顯示「開啟中…」，連上後變成「結束選取」）。
3. 把游標移到要講的區塊，看到框線後點下去。畫面上會多一個釘子，右側留言框顯示這張畫面的名稱和區域代號。
4. 在「你希望畫面如何調整？」用自己的話寫，例如：「姓名欄位下面加上字數上限說明，照現有表單的樣子。」
5. 按「儲存留言」。

**你會看到：**討論紀錄多一則「待處理」，寫著你的原文和對應的畫面。釘子留在畫面上，縮小看整體時也在，點釘子會跳到那則留言。重新整理網頁留言不會消失。

可以在不同畫面各留幾則再一起處理。右側的篩選按鈕（全部／聚焦中／各畫面）可以只看某一張畫面的留言。

**只能點 AI 已標記的區域，不能任意框選。** 如果框線範圍太大，或你想指的欄位點不到，回 CLI 跟 AI 說「這個區域要能單獨留言」，它會補標記。你不需要講 CSS 或元件名。把畫面「收起」或它被退回縮圖後，釘子會縮到標題列上，留言本身還在。

### 3.4 回 CLI 讓 AI 處理

回到 **3.1 的同一個 CLI session**，說一句就好：

```text
已留言
```

「處理本輪留言」、讀最新留言、也可以。

**你會看到：**AI 不會要你把留言重貼一遍。處理完後，瀏覽器右側同一則留言下面出現「代理回覆」，狀態變成「已處理」或「待釐清」。網頁約每 2 秒同步一次，AI 處理本身要花的時間另計。預覽有沒有自動更新看專案的 dev server，必要時重新整理。

| 狀態 | 意思 |
|---|---|
| 待處理 | 新留言、改過的留言，或畫面變動後需要重看的留言 |
| 待釐清 | AI 需要你或其他人做決定，回覆裡會列選項 |
| 已處理 | AI 改了、也看過畫面了。不代表你已經確認整版 |

你不用刪留言，也不用逐則按確認。

### 3.5 繼續討論同一則、或看其他狀態

**改留言：**在已處理的留言按「編輯留言」，改內容後按「儲存修改」。它會回到「待處理」，舊回覆還留著（那是上一輪的）。回 CLI 再說一次「已留言」。如果儲存時跳出「已有較新版本」，按「重新讀取最新版本（保留草稿）」，看一下最新內容再存。

**看載入中、儲存失敗這些狀態：**通常已經是畫布上不同的畫面，用上方流程按鈕切過去就好。還沒有的話跟 AI 說：

```text
先沿用目前 layout，帶我走過此功能的載入、儲存中、成功、驗證失敗、
儲存失敗、空資料與權限狀態；依 PRD 判斷哪些適用，逐一加進畫布。
未知規則保持提案或待確認，不要補出正式 API 或重試規則。
```

AI 加畫面後會重啟一次審閱服務，審閱網址通常不變，重新整理即可。畫面標的 state 是那張的起始狀態，不會隨你的操作改名。

AI 改某張畫面時，會連帶改那張畫面的版號並重啟審閱服務；那張畫面上的留言會回到「待處理」，該畫面之前的確認會顯示「已失效」。這樣你能明確知道哪些畫面需要重看，哪些不用。

### 3.6 確認版本，拿到交付文件

確認前先請 AI 列一下：哪些畫面看過了、目前版本、還有哪些待決定。

要確認時，在右側展開「**確認整個版本**」。表單最上面會先列出還沒決定的事：「還有 N 件事沒決定」，每件一行（畫面 · 問題）。你有三個選擇：按「**全部照目前畫面定案**」（每一件都記成「採用目前畫面（整版確認時決定）」，AI 之後要據此更新 spec）、按「**全部列為未決事項**」（把這些問題整段填進未決事項欄位）、或自己一件一件點候選答案／打字回答。

只要還有沒決定的事，「沒有需要保留的未決事項」勾選框會停用；先處理完上面的清單，勾選框才能用。處理完後填「確認人」和「確認文字」（例如「這版可以，作為實作參考」），填「接受的未決事項（每行一項）」或勾「沒有需要保留的未決事項」（兩者擇一），按「確認目前畫面版本」。

這個按鈕確認的還是畫布上**所有**畫面，不是只有你正在看的那張，所以每張都看過再按。

**你會得到**（在 3.1 指定的目錄）：

```text
.ui-canvas/<功能名稱>/
├── UI-SPEC.md             # 版面、操作、每個狀態怎麼呈現、文案
├── UI-HANDOFF.md          # 後續開發者入口：怎麼重啟預覽、證據、未決事項
├── feedback-ledger.json   # 所有留言、回覆、狀態、確認紀錄
├── review-manifest.json   # 畫布上有哪些畫面
└── screens/               # 預覽的來源（story 或入口）
```

按瀏覽器的確認按鈕只存一筆確認紀錄，**不會自動產生 spec**，要請 CLI 收尾。確認也不會把待處理留言清掉。

### 3.7 關掉，下次繼續

留言存在專案檔案裡，關網頁不會掉。請 AI 停掉它啟動的服務就好。

下次在同一個 repo 開 CLI 說：

```text
繼續 .ui-canvas/<功能名稱>/ 的 UI 討論。
請先讀 UI-HANDOFF.md、UI-SPEC.md 和 feedback-ledger.json，
依記錄重啟原預覽與審閱畫布，保留留言 ID、歷史和確認範圍。
```

留言和回覆都會在。AI 是從專案檔案接續，不是靠記得上次聊了什麼。

## 4. 怎麼判斷這輪做得好不好

**好的跡象：**

- 畫面是專案真實元件跑起來的，你可以打字、開對話框、切頁；不是一張圖。
- 「選取區域留言」點得到你想講的地方，框線範圍合理。
- UI-SPEC 對每一個會等待的操作（載入、儲存、刷新）都有一列狀態表：進行中、成功、失敗各長什麼樣、資料有沒有保留。
- PRD 沒定的規則（例如能不能清空、失敗要不要重試）被標成「待決定」並列出選項和決策人，不是 AI 自己補一條。
- PRD 沒定的規則出現在畫布上問你，不是藏在 spec 檔裡。
- 整個過程 AI 沒有要你講 CSS、元件檔名，或自己去改 JSON。
- 確認時被要求填未決事項或勾「沒有」，不會被默默記成空白。

**該退回去重做的：**

- 拿截圖或手刻的 HTML 說是可操作預覽。
- 只給你 Storybook 網址，沒有留言側欄。
- 自己加了重試按鈕、預設值或錯誤文案，卻沒標成提案。
- 你說「已留言」，它卻要你把留言貼過來。
- 改了正式產品程式碼（預覽用的 story、標記除外），或做了 commit。

## 5. 常見問題

| 問題 | 答案 |
|---|---|
| 打 `/ui-canvas` 沒反應，或 AI 還在用舊流程 | 確認安裝目錄下有 `SKILL.md`，然後開新 session。舊 session 不會讀到新 skill |
| 打開的是 Storybook，沒有留言面板 | 那是預覽網址，不是審閱網址。請 AI 給 local review 的本地網址 |
| 畫面只有縮圖，點裡面沒反應 | 縮圖不能操作。點一下縮圖或按「開啟即時畫面」變成活的 |
| 「選取區域留言」是灰的 | 正在編輯或儲存某則留言時會暫時變灰，先存或取消。剛開頁面還沒載入完也會灰一下 |
| 還沒選區域，留言框下面寫什麼 | 「要留言：先按上方「選取區域留言」，再點畫面上的區塊。」照著做就好 |
| 確認之後又改了畫面會怎樣 | 那張畫面的確認會顯示「已失效」，它的留言退回「待處理」。如果整張畫面被移掉，會顯示「畫面已移除」，AI 會一併刪除它的舊截圖 |
| 畫面開了卻一直空白或 loading，工具列說「0 個可留言區域」 | 預覽伺服器（Storybook 或 dev server）卡住了，改了程式碼後偶爾會這樣。請 AI 重啟它，然後重新整理審閱頁面 |
| 剛開的畫面又變回縮圖 | 同時最多 3 張畫面是活的，開第 4 張會收掉最早打開的那張。留言不受影響，再點一下就回來 |
| 想留言的地方點不到，或框線太大 | 回 CLI 跟 AI 說要對哪個區域留言，它會補標記。你不用改 CSS |
| 留完言 AI 沒動作 | 它不會自動偵測。回 CLI 說「已留言」 |
| AI 說處理完了，網頁上沒看到回覆 | 請 AI 確認回覆有寫進這個 feature 的紀錄檔，不是只在 CLI 講；也確認它改完預覽後有重啟審閱服務 |
| 我確認過的畫面怎麼變成「已失效」 | AI 改了那張畫面的版本。只有改過的畫面會失效，其他畫面的確認還在。重看那張，再確認一次。 |
| 儲存留言失敗 | 先不要重新整理（草稿會掉）。請 AI 檢查審閱服務有沒有還在跑 |
| 為什麼要 Node 20 以上 | 這是有測過、有支援的版本範圍（20 和 24 都跑過）。更舊的沒測，不保證 |
| 這會用很多 token 嗎 | 瀏覽器上的操作不呼叫模型。花 token 的是 AI 探索專案、改預覽、看畫面 |
| 想確認第二個開發者接手能不能懂 | 給他 `UI-HANDOFF.md`，不給對話紀錄。他應該能靠文件重啟預覽、說出哪些已確認、哪些待決 |

## 6. 進階

想自己手動啟動審閱服務、把工具接到非 Storybook 的專案，或排查預覽連不上的問題，看 [local review 技術說明](references/local-review.md)。一般使用不需要讀它。
